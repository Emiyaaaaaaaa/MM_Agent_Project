# 面试答疑准备（MM Agent）

## 1. 你在项目里做了什么？
- 负责后端路由分层、Graph 运行时重构、前后端契约统一、任务级密钥治理，以及高频故障修复。
- 重点工作是把故障点沉淀为工程约束：运行时生命周期管理、序列化边界定义、接口契约文档和问题复盘机制。

## 2. 最难的问题是什么？怎么解决的？
- 难点是 LangGraph 异步运行时与 checkpoint 的生命周期冲突，表现为 WS 流式链路中的状态更新异常。
- 处理方式是将初始化从 import 阶段迁移到 FastAPI lifespan，并引入 `GraphRuntime` 统一托管 async saver 生命周期。
- 同时将聊天链路统一为异步状态更新，消除 `update_state`/`aupdate_state` 混用。

## 3. 为什么要去掉环境变量 API Key 回退？
- 系统采用任务级 key 隔离。保留环境变量回退会导致凭据来源不确定，增加租户混用和审计风险。
- 移除回退后，凭据来源单一且可追踪，异常定位路径也更清晰。

## 4. 你怎么保证修复有效？
- 采用“症状-根因-修复-验证”闭环，并对关键改动执行编译、类型检查和联调验证。
- 修复结果同步记录到问题日志，保证后续复盘与交接可追溯。

## 4.1 你们为什么要做“纯结构化协议”？
- 字符串协议在多模态与多节点链路中会丢失语义边界（代码、公式、表格、图像混在同一文本字段）。
- 改为 `ContentBlock[] + stage` 后，前后端契约一致，可显著降低空输出误判和展示歧义。
- 结构化协议也是后续做契约测试、回放与审计的前置条件。

## 5. 技术选型为什么是这套？
- FastAPI：支持 HTTP 与 WebSocket，类型提示完整，接口开发效率高。
- LangGraph：适合多节点、可中断、可恢复的状态型流程编排。
- SQLite/Chroma：本地部署成本低，满足比赛和实验环境的交付约束。
- Vue3+Pinia：状态流清晰，适合实时事件驱动的 UI 渲染。

## 6. 如果让你继续演进，你会做什么？
- 补齐统一鉴权（JWT/Session）与细粒度权限边界。
- 完善测试体系：契约测试、WS 集成测试、E2E 回归测试。
- 增强可观测性：请求追踪 ID、节点耗时、错误分类指标。
- 按业务规模评估并演进存储架构。

## 6.1 为什么不允许节点任意安装依赖？
- 任意安装会引入供应链风险和环境漂移，且结果不可复现。
- 当前策略是受控自动安装：仅白名单包可安装，安装过程具备日志、超时和可回放能力。
- 对常见建模场景优先采用轻依赖实现（例如 `rankdata` 由 `pandas.Series.rank` 替代）。

## 6.2 为什么要把 Coder 从“单图输出”升级为“动态产物清单”？
- 数学建模场景通常需要多算法对比、多图、多表和多类导出文件，单图协议无法覆盖。
- 单 `artifact_url` 不能表达“同一轮输出多个资产”，也无法区分图片与文件类型。
- 方案是引入 `artifact_manifest`（`kind/url/filename/size`），后端基于执行前后文件快照自动生成并通过 WS 推送。
- 前端按 `kind` 渲染（图片预览、文件链接），并保留旧字段兼容以降低迁移风险。

## 6.3 为什么这次没有直接上 Alembic？
- 当前阶段目标是“兼容优先 + 快速收敛风险”，项目已有历史 SQLite 库且任务 ID 与线程 ID 强绑定，直接引入全量迁移框架会显著放大改造面。
- 本次采用“脚本化可审计迁移”先落地关键约束（软删除标准化、关键字段 NOT NULL、索引补齐），把高风险问题先收敛。
- 后续进入长期维护阶段，再将稳定后的 DDL 路线收敛到统一迁移框架（如 Alembic）更稳妥。

## 6.4 为什么迁移后要保留 `*_backup_v1` 备份表？
- 目的是把回滚路径前置为工程能力，而不是故障后临时处理。
- 对 SQLite 来说，重建表迁移是常见手段；保留备份表可在分钟级完成结构回退，降低恢复时间。
- 备份表保留策略配合回滚脚本和完整性校验，能形成可演练、可验证的恢复流程。

## 6.5 如何控制数据库迁移风险？
- 迁移前先做审计脚本（空值、孤儿外键、阻断项）和 dry-run 演练，避免盲目执行。
- 正式迁移采用事务包裹、前置守卫校验、行数一致性校验，失败即回滚。
- 迁移后立即执行 `foreign_key_check` 与 `integrity_check`，并核验索引与约束是否落地。

## 6.6 这次迁移里最容易被忽略的坑是什么？
- SQLite 索引名是全局唯一；保留备份表后，同名索引可能仍在备份表上，导致 `CREATE INDEX IF NOT EXISTS` 被误判为“已存在”。
- 处理方式是“先 `DROP INDEX IF EXISTS` 再 `CREATE INDEX`”，确保索引绑定到活动表。
- 这个问题不影响表结构迁移成功，但会影响查询性能和后续稳定性，必须在验收阶段显式检查。

## 7. 为什么要做“任务内重新开始”？
- 该系统是状态型 Agent，仅清空聊天记录不能重置运行态；保留 checkpoint 会导致流程继承历史状态。
- 采用“任务级双清理”：清空消息表并删除对应 task 的 graph checkpoint（`checkpoints`/`writes`）。
- 这样可以保证同任务原地重开且状态一致，避免隐性状态污染。

## 8. 30 秒项目总结
- 项目定位是面向数学建模场景的多模态 Agent 平台。
- 核心改造成果是工程化能力建设：统一契约、路由分层、异步运行时托管、任务级密钥隔离、问题日志闭环。
- 结果是系统稳定性、可观测性和可维护性提升，后续迭代成本下降。
